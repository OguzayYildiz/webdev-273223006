## 1. Live URL and how to verify it

The public deployment is pending. `course.json` has no live URL yet. The Render dashboard requires an authenticated account, and the persistent PostgreSQL and OAuth credentials will be configured in the provider dashboards.

How I checked: Local HTTP tests exercised `GET /health` and verified 200 with `{"status":"ok","db":"ok"}`. The same session could still see that lab after the application container was removed and recreated. ## 2. Environment variables

| Name | Purpose | Source |
| --- | --- | --- |
| PORT | Listen port | Render or local shell, defaults to 3000 |
| DATABASE_URL | Persistent PostgreSQL connection | Neon Connect, configured as a Render secret |
| SESSION_SECRET | Signs temporary Google state and PKCE information | Generated by the Render blueprint |
| PUBLIC_BASE_URL | Optional canonical HTTP origin | Set only when overriding the provider URL |
| RENDER_EXTERNAL_URL | Canonical origin on Render | Render-provided setting |
| GOOGLE_CLIENT_ID | Google web OAuth client ID | Google Cloud Console |
| GOOGLE_CLIENT_SECRET | Google OAuth client secret | Google Cloud Console, entered into Render |
| GEMINI_API_KEY | Optional key for text suggestions | Google AI Studio |
| MODEL_NAME | Model override | Defaults to gemini-3.5-flash-lite |
| MCP_TOKEN | Ordinary session token for local stdio project tools | Developer environment only |
| NEW_USER_PASSWORD | Password for an account provisioned by the CLI | Operator shell during provisioning only |

How I checked: The application, OAuth adapter and MCP entry point read these variables from the environment. `.env.example` contains placeholders and `.dockerignore` excludes local secret files.

## 3. What happens when things fail

- Database unavailable: `/health` returns JSON with 503. The test used a database adapter that raises an error and observed the public response without internal details.
- Google unavailable or misconfigured: Password sign-in remains available. Tests used a fake provider and checked invalid, expired and unverified callbacks as well as a verified login on the existing account.
- Invalid booking date: The browser displayed “Choose a valid date.”. An API test also observed 422.
- Bad release: The Render rollback and its duration still need live verification. The Lab 2 coverage job did fail on the failing code and kept the CI run red.

## 5. Request waterfall

The reservation screen's initial dependency chain is the HTML document, two linked assets in parallel (CSS and deferred JavaScript), then the availability request from the script. Booking adds one write followed by an availability refresh.

How I checked: The route and browser script show these dependencies. Browser timing was unavailable in the local inspection environment. A cache-disabled Network trace with elapsed time is pending for the public deployment.

## 6. Security basics checked

How I checked: Two signed-in test users and one signed-out request exercised authorization against the test database. The server returned 403 and 401 for disallowed cancellation, and only the owner could cancel. The OAuth test observed HttpOnly, SameSite=Lax and Secure on the resulting session cookie. A test confirmed that a digest of the session token is stored in the database. `node checks/ex2.mjs` passed its repository secret scan. The current history should also be checked before final hand-in.

## 8. Model feature

The submitted scheduling preference leaves the app for Gemini along with a limited list of candidate slot IDs, workstation labels, dates and hours. Account identifiers, email, cookies and other students' bookings stay inside the application. The service allows up to four seconds for the provider. With no key, a timeout, a rate limit or an unusable response, the manual controls stay available. The service checks that a suggested slot still exists and is available before showing it.

How I checked: The test suite uses fake clients to inspect the outgoing data, simulate rate limits and timeout, and verify the second availability check. The unconfigured browser showed a fallback message. ## 9. MCP

The lecture tools remain local. The project tools list free slots, reserve one slot, and list the current user's reservations. Project calls use an ordinary session token against the shared PostgreSQL connection. The booking service enforces the same rules for these calls and the REST API.

How I checked: The MCP protocol check passed 12/12. The project integration test covered missing and unrecognized tokens, availability, reservation, conflict and owner-only listing. A real external MCP client against the hosted database is pending.
